## 執筆指示書（原文）

本文は原文のまま。Markdown の見出しレベルのみ 1 段下げている（このファイルの H1 と衝突するため）。

### Azure 自習書 インデックスと執筆指示書（2026年8月 最新情報反映版）

#### 0. この本のコンセプト

Azureの学習でつまずく最大の原因は、個々のサービスの使い方を先に覚えてしまい、サブスクリプションやリソースグループといった土台の構造をあとから継ぎ足すことにある。この本は逆順を取る。最初にガバナンス階層(テナント・管理グループ・サブスクリプション・リソースグループ)を体に入れ、そのあとで個々のサービスを「その階層とどう繋がっているか」という縦の関係と、「認証認可・ネットワーク・課金とどう繋がっているか」という横の関係の両方から学ぶ。

読者は各章で必ず手を動かす。概念の説明だけで終わる章は作らない。操作した結果が、直前に説明した概念の具体例になっている、という往復を章の中で完結させる。

対応表による学習(他クラウドの用語に置き換えて理解する方法)は使わない。Azure独自の語彙と構造だけで理解が完結するように書く。

本書の核はPart 4の「6ブロックの型」である。サービスを6つに絞って型を深く固定し、扱わなかったサービスへは読者自身が型を適用して広げる設計とする(付録ワークシートと第21章がその受け皿)。

#### 1. 2026年時点の技術選定方針(執筆前に固定する前提)

本書の手順・記述は以下の現行推奨に揃える。旧方式は「レガシーとして存在する」ことだけ短く触れ、手順には含めない。

- Functionsのサーバーレスプランは Flex Consumption を標準とする。Microsoftが推奨するサーバーレスプランであり、Linuxベースで、VNet統合・インスタンスメモリ選択・Always Ready インスタンスを持つ。従来のConsumptionプランはLinux版が2028年9月30日に廃止予定のレガシーであり、本文の手順には使わない
- Azure Blueprints は2026年7月11日に廃止済み。ガバナンス配布の説明は Template Specs と Deployment Stacks、および Azure Policy + 管理グループ + IaC の組み合わせで書く。Blueprintsは「廃止された旧サービス」として1段落だけ言及する
- Landing Zone のIaC実装は Bicep の Azure Verified Modules (AVM) for Platform Landing Zone を正とする(GA済み、ALZアクセラレータの既定)。旧来のALZ-Bicep(クラシック)は2026年2月16日にアクセラレータから削除・リポジトリアーカイブ済みなので扱わない
- Deployment Stacks はライフサイクル管理の中核概念として第10〜11章で正面から扱う。テンプレートから消えたリソースを自動で掃除する挙動は「リソースグループ=ライフサイクル境界」の学びと直結するため、単なるツール紹介ではなく概念の実装として書く
- Key Vault の認可は Azure RBAC を正とする。API バージョン 2026-02-01 以降、新規Vaultの既定モデルはRBACになり、アクセスポリシーはレガシー扱い。第14章は「なぜ2つのモデルが併存しているか」という歴史込みで書くが、手順はRBACのみ
- AKS のPodからAzureサービスへの認証は Microsoft Entra Workload ID(OIDCフェデレーション + ユーザー割り当てマネージドID)を正とする。旧Pod-managed identityは廃止済みとして手順に含めない
- Cosmos DB は disableLocalAuth によるキー認証の無効化と、データプレーンRBAC(コントロールプレーンRBACとは別物で、ポータルのIAM画面から設定できない)を軸に書く
- Entra ID という名称で統一する(Azure ADという旧称は初出時に併記のみ)

執筆時は各章の冒頭で必ず該当サービスの公式ドキュメントの最新版を確認し、この方針リスト自体を更新すること。サービス仕様の変化は速く、本リストも陳腐化する。

#### 2. 全体構成

- Part 1 ガバナンス階層を体で覚える
- Part 2 認証と認可を分離して理解する
- Part 3 IaCでリソースを再現可能にする
- Part 4 サービス別に縦と横の繋がりを辿る(本の核)
- Part 5 大規模運用のための設計思想
- Part 6 総合演習
- 付録 型の適用シート

#### 3. 目次(インデックス)

##### Part 1 ガバナンス階層を体で覚える

第1章 テナントとサブスクリプション ― 契約と分離の境界
テナントは組織とIDの境界、サブスクリプションは課金・クォータ・リソースプロバイダー登録の境界。「リソースプロバイダー登録」という独自概念をここで先出しする。壊す演習: 未登録プロバイダーのサブスクリプションでデプロイして失敗を観察する。

第2章 管理グループ ― ポリシーとRBACが上から下に伝わる仕組み
継承の仕組みと、階層設計が後から動かしにくい理由。

第3章 リソースグループ ― ライフサイクルをまとめる単位の設計
「一緒に消えるべきものをまとめる」という設計原則。クリーンアップ演習: リソースグループを消したとき、何が一緒に消え、何が残るか(Entra ID側のオブジェクトは残る)を観察する。

第4章 [統合ハンズオン] 4階層を1つのシナリオで通しで作る
管理グループ作成 → サブスクリプション配置 → リソースグループ → リソース1つ、をaz cliで通しで実行し、各階層をポータルで確認する。

##### Part 2 認証と認可を分離して理解する

第5章 Entra IDの基本 ― ユーザー・グループ・サービスプリンシパル・マネージドID
IDの実体はテナントに属し、リソースはサブスクリプションに属する、というねじれをここで固定する。

第6章 RBAC ― スコープとロールの掛け算で権限が決まる
割り当てスコープ(管理グループ/サブスクリプション/リソースグループ/リソース)はガバナンス階層と独立に選べる点を強調。壊す演習: スコープを1段広く割り当てて権限が効きすぎる様子を確認し、最小権限に絞り直す。

第7章 マネージドID ― リソース間の内向き認証
システム割り当てとユーザー割り当ての使い分け。ライフサイクルの違い(システム割り当てはリソースと共に消える)をクリーンアップ演習で確認する。

第8章 外向き認証 ― アクセスキー・Entra ID認証・フェデレーションの使い分け
キー認証をポリシーで無効化していく現在の潮流(Key VaultのRBAC既定化、Cosmos DBのdisableLocalAuth)を、Zero Trustの文脈でまとめて予告する。

##### Part 3 IaCでリソースを再現可能にする

第9章 ARMテンプレートとBicepの関係
BicepはARM JSONへコンパイルされる純粋なオーサリング改善であり、ランタイム差はない、という一点を実際にbicep buildで確認する。

第10章 デプロイスコープとDeployment Stacks
テンプレートをリソースグループ/サブスクリプション/管理グループのどこに書き込むかというスコープ概念と、Deployment Stacksによるライフサイクル管理(テンプレートから消したリソースがactionOnUnmanageの設定に従って削除される)をセットで扱う。壊す演習: スタックからリソース定義を1つ消して再デプロイし、実リソースが掃除されるのを観察する。

第11章 モジュール化とAzure Verified Modules
自作モジュールの書き方と、公式レジストリのAVMモジュール(br/public:avm/...)の使い方。「検証済みモジュールを組み合わせる」という現在の標準スタイルに読者を接続する。

##### Part 4 サービス別に縦と横の繋がりを辿る

第12章 Functions ― Flex Consumptionを軸に課金とネットワークの関係を辿る
On Demand課金とAlways Readyインスタンスの違い、無料枠がサブスクリプション単位で集計される事実(契約階層との接続)、VNet統合がFlexで使える意味。ひな形章としてテンプレートを完全に守って書く。

第13章 Storage ― Functionsの隠れた依存関係から理解する
Function Appが必ずStorageを要求する理由(トリガー状態・デプロイパッケージ)から入り、リソースグループの「ライフサイクルをまとめる」原則の実例として扱う。

第14章 Key Vault ― RBAC既定化とアクセスポリシーの歴史
API 2026-02-01でRBACが新規Vaultの既定になった変更を教材化する。「同じサブスクリプション内に新旧2つの認可モデルのVaultが混在しうる」という運用上の罠を、実際に両方式のVaultを作って確認する。壊す演習: RBACロール未割り当てのままシークレット取得して403を観察する。

第15章 AKS ― 5つのID scenarioとWorkload ID
クラスタ自身のID、ノードのID、Podから外へのID(Workload ID = OIDCフェデレーション)、クラスタへのアクセス、クラスタ内RBACを分解する。KubernetesのServiceAccountとEntra IDのフェデレーションという二重構造が本章の山場。

第16章 Cosmos DB ― コントロールプレーンとデータプレーンのRBACは別物
データプレーンRBACがポータルのIAM画面から設定できず、独自のロール定義・割り当てを持つ点、disableLocalAuthでキー認証を止める構成、Azure Policyで組織的に強制する繋がり(第18章への布石)。壊す演習: disableLocalAuth有効化後にキーでアクセスして失敗を観察する。

第17章 Networking ― VNet統合とPrivate Endpointが各層にどう効くか
これまでの章で作ったFunctions・Storage・Key Vaultを閉域化し、ホスティングプラン/SKUの選択がネットワーク機能の可否に波及する構造を総括する。

##### Part 5 大規模運用のための設計思想

第18章 Azure Policy ― 強制(Deny)と監査(Audit)の違い
第16章のdisableLocalAuthを組織全体に強制するシナリオで、管理グループスコープへのポリシー割り当てを実践する。

第19章 Cloud Adoption FrameworkとLanding Zone
プラットフォームLanding Zoneとアプリケーション Landing Zoneの分離、サブスクリプションを管理単位とする思想。実装はAVM for Platform Landing Zone(Bicep)を読み解く形で扱い、全部をデプロイはしない(コストと権限の問題)。読む教材として使う。

第20章 マルチサブスクリプション設計の実践
ワークロード×環境ごとにサブスクリプションを分ける現在の推奨と、サブスクリプション自動払い出し(subscription vending)の考え方。

##### Part 6 総合演習

第21章 1つのアプリケーションをゼロから設計し、全階層を貫通させる
Part 1〜5の概念を全て使う設計にする。さらに本文で扱っていないサービスを1つ(Service Busを想定)あえて組み込み、未習サービスでも6ブロックの型で読み解けることを読者に体験させる。これが本書の主張の証明になる。

##### 付録 型の適用シート

6ブロックのテンプレートを空欄のワークシートにし、本文で扱わなかったサービス(App Service、Container Apps、SQL Database、Service Bus、Monitor/Log Analytics、Front Doorなど)を読者自身が埋める演習とする。模範解答を1サービス分(App Service)だけ付けて自走できるようにする。

#### 4. 各章の執筆テンプレート(6ブロック)

Part 4は以下の6ブロックで統一して書く。第12章を標準形として、以降の章も型を崩さない。

1. このサービスは何のためにあるか(3行以内)
2. 縦の依存関係 ― テナント/管理グループ/サブスクリプション/リソースグループが、このサービスの挙動にどう効くかを具体的に書く。効かない層があれば、効かない理由も書く
3. 横の繋がり(認証認可) ― 内向き(このサービスから他へのアクセス)と外向き(このサービスへのアクセス)を分けて書く。RBACのスコープ選択がガバナンス階層と一致するとは限らない点を毎章明示する
4. 横の繋がり(インフラ足回りとネットワーク) ― ホスティングプランやSKUの違いが、ネットワーク機能や可用性にどう波及するか
5. 横の繋がり(契約・課金) ― 従量課金と専有課金のどちらに属するか、課金・無料枠がどの階層で集計されるか。ハンズオン後にCost Managementで「いま作ったものが課金上どう見えるか」を確認する1コマンドを置く
6. ハンズオン ― az cliまたはBicepで構築する手順。壊す演習(意図的に失敗を再現して概念を確認する)とクリーンアップ演習(削除時に何が消え何が残るかの観察)を必ず含める。手順の最後に、1〜5で説明した概念がどう確認できたかを短く振り返る

Part 1〜3、Part 5の章は、この型のうち該当するブロックだけを使う。無理に6ブロック全部を埋めない。

#### 5. 章末の理解チェックの作り方

各章の末尾に、暗記の再現ではなく応用を問う設問を3問置く。

- 良い例: 「Flex ConsumptionのFunction Appをリソースグループごと削除すると、ユーザー割り当てマネージドIDも一緒に消えるか。消えない場合、どこに残るか」
- 避ける例: 「Functionsのホスティングプランを3つ挙げよ」(暗記の確認に留まり、繋がりの理解を測れない)

#### 6. 執筆上の注意点

- 概念の説明のあとに必ず具体的な操作を置く。抽象だけで段落を終えない
- 他クラウドとの対応表や比較は本文に出さない。読者がAzure外の知識を持っているかどうかに依存しない書き方にする
- サービスの機能を並べるだけの節を作らない。「なぜその構造になっているか」を必ず一文添える
- 実行コマンドは実際に動くものだけを書く。検証していない手順は書かない。検証時のCLIバージョンとAPIバージョンを章内に記録する
- レガシー方式(Consumptionプラン、アクセスポリシー、Pod-managed identity、Blueprints)は「存在したこと・なぜ置き換わったか」を1段落で触れるに留め、手順は現行推奨のみで書く
- コストは無料枠と低額SKUで完結する構成を前提にする。無料枠を超えうる箇所(AKSなど)は章の冒頭に概算を明記する
- 図が必要な箇所(特にPart 1のガバナンス階層、第15章のID構造、第17章の閉域化構成)は、本文中に「ここに図: (図の内容)」と書き添えて、後工程で図版を作成する

#### 7. 執筆の進め方

1. まずPart 1(第1〜4章)を書き切り、実際に自分で第4章のハンズオンを通しで実行して手順の欠落がないか確認する
2. Part 2、Part 3も同様に書いてから検証する
3. Part 4は第12章(Functions)を先に書き、テンプレートとして固定してから第13章以降を書く
4. Part 5、Part 6、付録は最後に書く。第21章はPart 1〜5で登場した概念を全て使い、未習サービスを1つ含める設計にする
5. 脱稿前に「1. 技術選定方針」を公式ドキュメントで再検証し、廃止日・API バージョン・推奨の変更を反映する
