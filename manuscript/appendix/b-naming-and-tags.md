# 付録B 命名規約とタグ設計

第4部の各章が持つ「契約・課金」ブロックは、タグによるコストの按分を前提にしています。本付録はその前提の設計をまとめます。第23章と対で機能します。

## 名前の制約はリソース種別ごとに違う

本書の実測で踏んだ制約を並べます。

| リソース             | 一意性の範囲         | 文字の制約                     | 実測での現れ方                                         |
| -------------------- | -------------------- | ------------------------------ | ------------------------------------------------------ |
| ストレージアカウント | 世界                 | 英小文字と数字のみ、3〜24 文字 | StorageAccountAlreadyTaken（第15章。世界の誰かと衝突） |
| Key Vault            | 世界                 | 英数字とハイフン、3〜24 文字   | 論理削除中も名前が 90 日予約される（第3章・第16章）    |
| リソースグループ     | サブスクリプション内 | 比較的自由                     | 同名を別サブスクリプションに作れる                     |
| Service Bus 名前空間 | 世界                 | 英数字とハイフン               | 第24章で作成時に一意名を要求される                     |

世界一意のものは DNS 名になるから、という理由（第15章）を知っていれば、この表は暗記でなく導出できます。設計上の帰結は 2 つです。

1. 世界一意のリソース名には、衝突を避ける識別子（サブスクリプション ID の断片など）を機械的に混ぜます。本書のスクリプトが `azpch15$(サブスクリプションIDの先頭8文字)` の形を使っていたのがこれです
2. ハイフン不可・文字数上限のあるリソースが混ざるため、命名規約は「全リソース統一の 1 パターン」ではなく「基本形 + 種別ごとの縮退規則」として設計します

基本形の例（本書の検証で使った形の一般化）です。

```text
<プロジェクト>-<用途/章>-<リソース種別>     例: azp-ch15-rg
<プロジェクト><用途><一意化子>              例: azpch15abcd1234（ハイフン不可のもの）
```

名前に環境（dev / prod）を含めるかは組織の流儀ですが、第22章の「サブスクリプションで環境を分ける」設計を採るなら、名前に環境を刻む必要性は下がります。境界に語らせるか、名前に語らせるかの選択です。

## タグの設計

### 何を付けるか

本書のハンズオンが全リソースグループに付けてきた 3 つが、最小構成の例です。

| タグ          | 役割                       | 使った場面                                      |
| ------------- | -------------------------- | ----------------------------------------------- |
| azp-book      | 何のプロジェクトか（帰属） | 検証環境の棚卸し                                |
| azp-chapter   | 何のためか（用途の細分）   | teardown の対象特定、コストの章別按分（第23章） |
| azp-lifecycle | 消してよいか（運用指示）   | ephemeral = 発見次第消してよい、の明示          |

組織で設計するなら、帰属（部署・プロジェクト）、用途（環境・サービス名）、運用（管理者連絡先・廃止予定日）の 3 系統から、コスト照会と運用自動化で実際に使うものだけを選びます。使われないタグは腐り、腐ったタグは信頼されなくなります。

### タグは継承されない

第3章で述べたとおり、リソースグループのタグは中のリソースへ自動では付きません。コスト按分をリソース単位で正確にやるには、リソース自身にタグが要ります。

手で徹底するのは不可能なので、強制は第20章の Azure Policy が受け持ちます。組み込みポリシーに「必須タグがなければ拒否する（Deny）」「リソースグループのタグを継承させる（Modify）」の系統が用意されており、管理グループスコープに割り当てれば組織全体の既定になります。タグ設計は、ポリシー設計とセットで初めて実効性を持ちます。

### タグとコストの接続

タグ軸のコスト照会（第23章の grouping を TagKey にする形）が、この付録の設計の出口です。タグは付けた時点から先の課金にしか効かないため、「最初から付いている」ことに価値があります。払い出し（第22章）の初期設定にタグを含めるのはこのためです。
