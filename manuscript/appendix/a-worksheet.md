# 付録A 型の適用シート

本書が Part 4 で固定した 6 ブロックの型を、本文で扱わなかったサービスに読者自身が適用するためのワークシートです。第24章で Service Bus に対して行った読解を、任意のサービスで再現するための道具です。

対象候補は App Service、Container Apps、SQL Database、Monitor / Log Analytics、Front Door などです。模範解答は App Service の 1 サービス分だけを付けます。1 つ埋まっていれば残りは自走できます。

## ワークシート（空欄）

新しいサービスに向き合うとき、次の問いを順に埋めてください。埋めるための最初のコマンドも添えてあります。

### 1. このサービスは何のためにあるか

3 行以内で書きます。機能の列挙ではなく、何の問題への答えかを書きます。

### 2. 縦の依存関係

| 階層               | このサービスへの効き方 |
| ------------------ | ---------------------- |
| テナント           |                        |
| 管理グループ       |                        |
| サブスクリプション |                        |
| リソースグループ   |                        |

確認の入口: リソースプロバイダーは何か、登録済みか（`az provider list`）。名前の一意性はどの範囲か。クォータは何の単位か。

### 3. 横の繋がり ― 認証認可

| 問い                                                                                                 | 答え |
| ---------------------------------------------------------------------------------------------------- | ---- |
| キー（ローカル認証）を持って生まれるか。止められるか（disableLocalAuth 相当の設定はあるか）          |      |
| データプレーンのロールは ARM の RBAC にあるか、独自世界か（`az role definition list --name` で探す） |      |
| マネージド ID を載せられるか（`--assign-identity` 相当はあるか）                                     |      |
| RBAC のスコープはどこまで細かく掛けられるか                                                          |      |

### 4. 横の繋がり ― インフラ足回りとネットワーク

SKU / プラン / tier の一覧を眺め、何が変わるのか（性能・冗長性・ネットワーク機能）を書きます。VNet 統合・Private Endpoint への対応が SKU で変わるかを必ず確認します。

### 5. 横の繋がり ― 契約・課金

従量か専有か。無料枠はあるか、あるならどの単位で集計されるか。作っただけで課金が始まる要素（時間課金）はどれか。

### 6. ハンズオン

最小の構成を 1 つ作り、壊す演習（意図的な失敗）とクリーンアップ演習（何が消え何が残るか。論理削除の有無）を設計します。実行した出力を記録します。

## 模範解答: App Service

本書の検証環境での実測（第1章・第14章の過程で得たもの）と、公式ドキュメントからの読み取りを分けて書きます。この書き分け自体も型の一部です。

### 1. 何のためにあるか

Web アプリケーションや API を、サーバーの管理なしでホストするサービスです。常駐プロセスを前提とする点が、イベント駆動の Functions との役割の違いです。

### 2. 縦の依存関係（実測あり）

リソースプロバイダーは Microsoft.Web で、作りたてのサブスクリプションでは未登録でした（第1章で実測）。さらにクォータが特徴的で、本書の検証環境では App Service の仮想マシン枠（Total VMs）の上限が 0 であり、無料の F1 プランですら作成できませんでした（第14章の経路で実測。エラーは「Operation cannot be completed without additional quota. Current Limit (Total VMs): 0」）。新しいサブスクリプションでは、プラン作成の前にクォータの引き上げ申請が必要になりえます。

### 3. 認証認可（公式ドキュメントからの読み取り）

マネージド ID（システム・ユーザー割り当てとも）を載せられます。発行証明書やデプロイ資格情報などのローカルな秘密も持つため、基本認証（FTP・SCM）を無効化する設定が用意されています。第8章の型（キーを止めて ID に寄せる）がそのまま適用できます。

### 4. 足回りとネットワーク（公式ドキュメントからの読み取り）

課金と機能の単位は App ではなくプラン（App Service Plan）です。Free / Basic / Standard / Premium の tier で、スケール台数・スロット・VNet 統合の可否が変わります。VNet 統合は Basic 以上、という「プランがネットワーク機能を決める」構造は第19章の総括どおりです。

### 5. 契約・課金（実測 + 読み取り）

プランは専有課金で、App が 0 個でもプランの VM 分が課金されます。ここが従量の Flex Consumption（第14章）との最大の違いです。同じ Microsoft.Web 配下の 2 サービスが、課金の哲学では正反対にいます。

### 6. ハンズオン設計（案）

クォータ引き上げ後、F1 プラン + App を作り、壊す演習は「プランだけ残して App を消し、課金が続くことを翌々日のコスト照会で確認する」（第23章の遅延を織り込む）。クリーンアップはリソースグループ削除で、プランと App が一緒に消えることを確認します。
