# 第 22 章 マルチサブスクリプション設計の実践

第 1 章で「分ける必要がないならサブスクリプションを増やさない」と述べました。組織の規模になると、この判断は逆転します。分けることで得られる分離（課金・クォータ・統制）が、増えることの管理コストを上回るからです。本章は、いつ・どう分けるか、そして量産をどう自動化するかを扱います。

本章の確認コマンドの出力は、本書の検証環境での実測です（識別子は伏せています）。

## 分ける単位 ― ワークロードと環境の組

現在の推奨は、ワークロードと環境の組ごとにサブスクリプションを分ける形です。

| サブスクリプション | 中身            |
| ------------------ | --------------- |
| app-a-prod         | アプリ A の本番 |
| app-a-dev          | アプリ A の開発 |
| app-b-prod         | アプリ B の本番 |

第 1 章の 3 つの境界が、この設計の根拠をそのまま与えてくれます。課金はワークロード別・環境別に自然に分かれ、開発の実験が本番のクォータを使い切ることはなく、リソースプロバイダーの登録状態も環境ごとに独立します。さらに第 2 章の管理グループと組み合わせれば、prod 系と dev 系で統制の強度を変えることも、サブスクリプションの置き場所だけで表現できます。

リソースグループでの分離との使い分けは、第 3 章の言葉で言えばこうなります。ライフサイクルを分けたいならリソースグループを、契約と統制を分けたいならサブスクリプションを使います。

## 増やすと何が大変になるか

サブスクリプションを増やす管理コストの正体は、初期設定の反復です。新しいサブスクリプションが来るたびに、管理グループへの配置、共通タグ、予算アラート、監査ログの送り先、ネットワークの接続、基本の RBAC を、毎回同じように設定することになります。

手作業でやれば、いつか設定漏れのサブスクリプションができます。第 20 章のポリシーは配置後の統制を自動化しますが、配置そのものは別の自動化が要ります。それが払い出し（subscription vending）です。

## 払い出しの自動化 ― subscription vending

考え方は単純で、「サブスクリプションを 1 つ作って初期設定まで済ませる」を、申請から完了までパイプラインにします。

```mermaid
flowchart LR
  REQ["申請 (ワークロード名・環境・予算)"] --> PIPE["パイプライン"]
  PIPE --> CREATE["サブスクリプション作成 (alias API)"]
  CREATE --> MG["管理グループへ配置 (第 2 章)"]
  MG --> BASE["初期設定 (タグ・予算・RBAC・ネットワーク)"]
  BASE --> DONE["利用者へ引き渡し"]
```

実装も公式のパターンモジュールが存在します。第 12 章・第 21 章と同じ方法で実在を確かめられます。

```bash
curl -s https://mcr.microsoft.com/v2/bicep/avm/ptn/lz/sub-vending/tags/list
```

```text
bicep/avm/ptn/lz/sub-vending
['0.6.1', '0.7.0', '0.8.0']
```

このモジュールが、作成・配置・タグ・ネットワーク・RBAC の一式を宣言として受け取ります。第 0 章で私たちがポータルで手作業した「サブスクリプションを作る」を、組織はコードで量産するわけです。

## 前提になる契約の形

プログラムからのサブスクリプション作成には、課金アカウント側の対応が必要です。自分の課金アカウントの種別は確認できます。

```bash
az billing account list --query "[].{name:name, type:agreementType}" -o json
```

```text
[
  {
    "name": "<課金アカウントID>",
    "type": "MicrosoftCustomerAgreement"
  }
]
```

本書の検証環境（第 0 章で作った従量課金）は MicrosoftCustomerAgreement（MCA）でした。現在の個人・中小向けサインアップは MCA になり、MCA と Enterprise Agreement（EA）はプログラムからの作成に対応しています。作成の権限は Azure の RBAC ではなく課金アカウント側のロール（請求プロファイルや請求書セクションへの権限）で決まる、という点が本書で初めて出てくる第 3 の権限体系です。ID の世界（第 2 部）とリソースの世界（第 1 部）に加えて、契約の世界にも独自のロールがある、と地図を更新してください。

なお、本書ではサブスクリプションの実作成は行いません。作成は課金を伴う契約行為であり、検証で量産すべきものではないからです。ここまでの確認（アカウント種別とモジュールの実在）が、読者の環境で払い出しを設計する際の出発点になります。

## 理解度チェック

1. 「環境ごとにリソースグループで分ければ十分では」という意見に対し、サブスクリプション分割でしか得られない分離を 3 つ、第 1 章の境界から挙げてください
2. 払い出しパイプラインの初期設定に「予算アラート」を必ず含めるべき理由を説明してください。サブスクリプションが課金の境界である（第 1 章）ことと、無料枠がサブスクリプション単位で集計される（第 14 章）ことを手がかりにしてください
3. サブスクリプション作成の権限を持つのは誰か調べることになりました。第 6 章で見た Azure の RBAC のロール割り当て一覧を調べても見つからないのはなぜですか
