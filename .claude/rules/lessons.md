# 指摘の教訓（繰り返し禁止）

同じ指摘を二度受けないための学習ファイル。指摘を受けたら 1 行追記する。
増やしすぎない。重複した行・陳腐化した行は削る。詳細は WRITING_GUIDELINES.md に置き、ここには規則だけを書く。
規則を追加するときは検出器（scripts/lint/）を同時に作る。散文だけの規則は破られた実績がある（未定義語で 4 回再発 → terms-lint 化）。機械化できない規則はここに残すが、数を最小に保つ。

行末に lint の名前が書いていない規則は、人が読んで守るしかないものである。指摘を受けたら、まずその規則が機械化できないかを疑う。このファイルの規則の半分近くは、最初は散文だけで、破られてから検出器になった。

検出器そのものも保守する。`npm run lint:self` が、原稿に違反を注入して各検出器が実際に落ちることを確かめる（CI でも走る）。動かない検出器は無い検出器より悪い。CI の緑が「守られている」ではなく「検査していない」を意味するようになるためである。検出器を直したり規則を書き換えたりしたら、この自己検査に対応する probe も直す。

## 文章

- ですます調。常体禁止。対句や言い切りで効果を出したくなっても地の文はですます調にする（「権限は足りている、それでも作れない」→「権限は足りているのに作れません」）。引用の中は話し手の言葉なので対象外（structure-lint が検査する）
- 太字禁止。どこが重要かは読者が決める
- 英語の概念語は「日本語 +（英語）」の対訳で書く（物理削除（purge）等）。コマンド名・製品名はそのまま
- 未定義の語・略語の禁止（図のラベルも同じ）。第 0 章の基本用語の表か初出で定義する。例の固有名（platform 等）は図の前に導入し、枠組み語（効く・内向き・プレーン等）は初出定義 + glossary 登録で順序を lint に守らせる
- 図に初見のサービス名・ロール名を置かない。図より前の本文で 1 文導入する（terms-lint が図のラベルの英語固有名を検査する）。図はその章で最初に目に入る場所で、そこで止まらせると本文まで届かない
- 秘匿感を出さない。「実は」「意外に感じる事実を 1 つ」「種明かし」は、事実を出し惜しみして読者を待たせる。知ってほしいことは最初の文で言い切る（禁止語は glossary）
- 擬人化しない。リソースや ID は「いる」ではなく「ある・定義されている」、「振る舞う」ではなく「動作する」、「顔」ではなく「側面」、「相棒」ではなく「依存先」、「運命を共にする」ではなく「同時に消える」。助数詞も人や生き物のものを使わない（サービスプリンシパル 47 体 → 47 種類）。技術文書の読者は、対象が生きていない前提で読む（禁止語は glossary、terms-lint が検査する）
- 章の主題を抽象名詞ひとつで名付けない。「本章で固定したいのは 1 つのねじれです」は、何と何がどうなっているのかを読者に想像させる。「A は X に属し、B は Y に属します」と平叙文で書く（ねじれ・歪み・手触り・勘所は glossary の禁止語）
- 雑な定義禁止。それ自体が説明を要する語で定義した気にならない。読者は Azure 初心者
- 入口の手順（アカウント作成・サブスクリプション作成など）を飛ばさない
- 出力は「読みどころがあるとき」に載せる（主張を裏付ける・成否を判断できない・実測が意外）。作成のたびに貼らず、確認の手に集める。各章に実出力 1 つ以上は lint が強制する
- 実測で踏んだエラーも全文で載せ、意味・成功しているのに失敗に見える場合の見分け方・駄目なときの進み方まで書く。伏せると読者は自分の環境を疑う
- 演習はコピペで頭から通る完全な列で書き、実際に打った出力を貼る。コマンドは 1 ステップ 1 ブロック、説明は本文へ（bash 内の行頭コメントは lint が落とす。ブロック内に独立したコマンドを 2 つ以上並べるのも lint が落とす。作る・確認する・消すは別のステップ）。シェル変数は使う前のブロックで代入する。スクリプト側にだけ代入がある状態は、本文がコピペで通らないということ（structure-lint が落とす）。「作ってあるとします」禁止。他の章の成果物への依存も禁止（別章リソースの参照と group create の欠落は lint が落とす）
- 確認済みの癖への対抗: 概念の説明が抽象語・造語に逃げる（→ できること・存在理由・具体例の順で書く）、図解が足りない（→ 章に図 1 枚以上を lint で強制）、主要テーマの初見情報が足りない（→ その章だけで理解できるか自問する）、図のノードが種類を語らない（→「prod (本番) 管理グループ」のように名前 + 種類で明記）
- 理解度チェックはその章の本文とハンズオンの範囲だけで解けるものにする。未習の章の知識を前提にしない。設問で使う語はその章の本文にも出す（用語集の初出章が前でも足りない。terms-lint が検査する）
- 枠組み語の定義を括弧の中に隠さない。独立した文で「本書では〜と呼びます」と書く（teardown を第 3 章の文末の括弧で定義していて、第 4 章の設問で読者が詰まった）。そもそも比喩の造語を作らない。既存の語で書けるなら作らない（投影 → テナントの台帳の 1 行、ID を載せる → ID を割り当てる。公式の CLI やドキュメントが使う動詞をそのまま採る。禁止語は glossary、terms-lint が検査する）
- 普通の意味を持つ語を専門用語としても使う章では、両方の意味を並べて分ける。第 5 章は「アプリケーション」をプログラムの意味と Entra ID の登録内容の意味の両方で使い、後者を括弧の中の「設計図」1 語で済ませていた。機械検査できない規則である
- 語の定義は、その語を最初に使う場所に置く。章の冒頭で定義して、直後の図や本文が別の語で進むと、読者は定義と図のずれを疑う（第 7 章はコンテナーを冒頭で定義し、次の図はリソース一般で描いていた）。機械検査できない
- 短所や制約を並べた段落は、誰の短所かを主語で明示する。第 7 章は password の短所を 3 つ並べた直後にマネージド ID の段落を置き、マネージド ID の短所だと読まれた。長所だけを書いた概念には制約も 1 段落で添える。機械検査できない
- 造語の指摘は、最も上流の層で答える。語を決める 3 層のフィルター（WRITING_GUIDELINES 第 8 条）の層 1 は方針（操作の語は az のコマンドやフラグから採り、docs/vocabulary.json に出典を書く）、層 2 は文脈（「〜と呼びます」で決めた語は用語集に登録する）、層 3 は語（言い換え表と語彙スナップショット）。層 3 に 1 語足して終わりにすると、同じ形の造語が別の章で出る（vocab-lint が検査する）
- 文脈なしに出る多義語は、その章のその場で注釈する。用語集への登録も前章での定義も代わりにならない。コンテナーは実行環境の意味とストレージの入れ物の意味があり、第 7 章は定義せずに前者を使っていた。「ここでの◯◯は…」を初出の近くに置き、紛らわしい相手は BLOB コンテナーのように限定して書く（terms-lint が検査する）
- 章タイトルは `第 N 章 主題 ― サブタイトル`。角括弧のラベルも `統合` の類の修飾語も足さない。部の末尾のハンズオン章は `第 N 章 ハンズオン ― …`（structure-lint と terms-lint が検査する）
- ASCII と日本語の境目は半角スペースを 1 つ空ける（`第 4 章` `付録 B` `404 という顔`）。全角の約物との隣接は詰める。コマンドと実出力のブロックは触らない（structure-lint が検査する）
- 章の区分は `第 1 部` と書く。`Part 1` も `第一部` も禁止（structure-lint が検査する）。読者が辿る単位を 章 と 部 に揃える
- 比喩は実体と合うものだけ使う。ガバナンス階層は物を載せる台ではなく、リソースを置く場所と、そこに効く権限やルールを決める土台。「4 階層の上に載せる」のような言い方は、管理グループを物理的な台と錯覚させる
- 数だけで指さない。「4 階層」「3 つの軸」と書くときは、何のための 4 つなのかを同じ文で言う。数え上げは読者の頭に残らない
- ポータルの手順は、書くときも直すときも、毎回ブラウザで実画面を開いて確かめる。1 行の修正でも記憶で書かない。UI は頻繁に変わり、タブ構成・既定タブ・列名・日本語表示名が入れ替わる（第 4 章に、現行ポータルに存在しないチェックボックスを操作させる手順が残っていた）。機械検査できないので、画面の話に触れたら開くところから始める
- 理解の指示は肯定形。「別のロールだと思わないでください」→「同じロールとして読んでください」。一度そう思わせてから打ち消させると読者の手数が増える。禁止（本番で実行しないでください）と事実の否定はそのままでよい（structure-lint が認知動詞の否定形だけを落とす）
- 節の見出しの語と本文の語を揃える（見出し「継承」→ 本文「流れる」の言い換えは読者の頭に「？」を出す）。「名前を引く」のような業界口語も避け、正確な動詞（取得する・解決する・問い合わせる・引用する）を使う（structure-lint が検査する）
- 「掛ける」を使わない。割り当てる・適用する・設定する・作成する のうち実際の操作を書く。「掛け算」も組み合わせと書く（費用が掛かるは対象外。structure-lint が検査する）
- 同じ操作を同じ段落で言い換えない。「ロールの割り当ては、階層のどこにでも掛けられます」は 1 文で割り当てと掛けるが混在していた。動詞を 1 つに固定する
- リソースが「生まれる」と書かない。作られる・できる・出る と書く（structure-lint が検査する）

## セキュリティ

- 顧客名・実在のテナント/サブスクリプション ID・個人ドメインを書かない。例はダミー値。新しい実値に触れたら structure-lint の拒否リストへ追加
- 出力に混ざるオブジェクト ID・principalId・appId・UPN もダミーにする（個人に辿り着く）。組み込みロール定義 ID と組み込みポリシー定義 ID は公開値なので実値でよい。同じ実値は同じダミーへ写し、値の一致が説明になっている箇所を壊さない
- 伏せ方は先頭 8 桁だけ残す形にしない。それ自体が実値である（第 5 章で 8 桁だけ残した実績がある）

## 運用

- push の前に `npm run lint` と `npm run lint:self` を通す。検出器が黙っていない状態で送る
- 規約を 1 条でも足したら `WRITING_GUIDELINES.md` の規約版を進め、全章をその条で読み直して `docs/prose-review-log.md` の版を更新する。済むまで `lint:review` が落ちる。規約だけが進んで原稿が取り残されると、読者が開いた章が毎回「現行規約での初読」になり、同じ指摘が章ごとに出続ける（全 27 章が規約 8〜15 条の時点で書かれ、38 条まで増えた実績がある）
- push したら CI の結論を確認する。落ちたら次の作業より先に直す
- 指摘を 1 件直したら、同じ癖が他章に無いかを全章で洗い、規約と検出器を足すまでを 1 セットとする。1 箇所だけ直して終わると、同じ指摘を別の章で受ける
- 作業ブランチは切らない。コミットは main へ直接入れ、push まで済ませる（手順は `.claude/rules/git-workflow.md`）
- 章は自分がこのセッションで実行して得た出力だけを元に書く。他者から報告された出力は、自分で再現してから載せる。再現できなければ、その旨と出所を書く。因果の推定を事実の形で書かない
- 検証していない手順を verified にしない。実測と公式ドキュメントの差の例は WRITING_GUIDELINES の罠リストを見る
- 原稿を書き換えるスクリプトは、整形（prettier）まで済ませて終わる
